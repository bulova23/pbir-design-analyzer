# PBIR Design Analyzer v1.0 Consolidation and Stabilization Design

**Status:** Planning artifact based on repository validation at commit `a67af7ad` on 2026-08-21.

## Goal

Prepare a credible v1.0 path for the existing PBIR Design Analyzer workflow by restoring release discipline, freezing and characterizing behavior, proving the packaged product, consolidating architectural boundaries, and adding automated controls that make the current defect classes difficult to reintroduce. This effort does not add roadmap capabilities.

The supported workflow to protect is:

**Discover → Score → Understand Evidence → Prioritize → Preview → Fix/Rollback → Deliver**

## Evidence-based verdict

`docs/pbir-analysis.md` is directionally accurate, but it mixes current release blockers with architectural improvements and historical documentation. The repository state confirms the following classifications:

| Analysis finding | Classification | Severity decision |
|---|---|---|
| Main is failing CI | Confirmed | v1.0 blocker until the exact shared failure is classified and CI is green |
| Scoring/UI monoliths | Confirmed | high maintainability risk; not an immediate blocker if behavior is characterized first |
| Broad provider/experimental backend architecture | Confirmed with qualification | architectural/security review risk; not proof that dormant code is reachable from production |
| Release target/documentation/automation disagreement | Confirmed | v1.0 blocker because supported artifacts and release output disagree |
| No standard packaged PBIR acceptance path | Confirmed | v1.0 blocker for product confidence; unit tests alone are insufficient |
| C#/TypeScript contracts are manually broad | Confirmed with qualification | high contract risk; existing versioned guards are useful but not mechanical compatibility |
| Checked-in generated backend artifacts | Confirmed | provenance and stale-artifact risk; disposition requires an explicit decision |
| Roadmap/current-state documentation drift | Confirmed with qualification | release/current-state authority must be corrected; historical docs may remain historical |
| Missing lint/security/dependency gates | Confirmed | release-control gap; prioritize lint, dependency/security policy, and provenance by risk |
| Product scope is broadening | Confirmed | scope-control problem; classify current capabilities before any new roadmap work |
| Telemetry reporter is a no-op | Confirmed | observability contract is misleading but not a v1.0 blocker if explicitly documented or removed from active expectations |

### Findings not accepted mechanically

- The analysis’s proposed multi-assembly split is not yet approved. First map the actual composition root and dependency graph; start with namespaces/modules and architecture tests unless the graph proves assembly isolation is needed.
- The analysis’s suggestion to move all provider/research code out of the shipped assembly is qualified. The current `PbirDesignAnalyzer.Core.csproj` compiles a broad `Services/Discovery` tree, but `RpcHost/AnalyzerRpcDispatcher.cs` exposes a narrower set of routes. Reachability and transitive dependencies must be measured before deciding what remains packaged.
- The analysis’s “no acceptance path” statement means no authoritative standard release gate, not that no smoke scripts or historical validation exist. Existing scripts such as `phase2-packaged-bundle-smoke.mjs` and `verify-backend-targets.mjs` should be reused or retired deliberately.
- The telemetry no-op is intentional according to the implementation and tests. The decision is whether to remove misleading production instrumentation or document it as a disabled seam; it is not evidence of data leakage.

## Release blockers versus improvements

### Blockers before v1.0

1. `main` must have green required CI, including the three OS matrix jobs, with the current failure diagnosed from run `32268663692` and no test weakening.
2. One authoritative supported-target contract must drive packaging, runtime descriptors, artifact names, README text, release docs, and release workflow. The current five-target documentation and four-target release matrix cannot coexist.
3. Release authority must be unambiguous: GitHub Release creation, Marketplace publication, manual upload, secrets, and rollback must agree with the authoritative release guide.
4. A sanitized versioned PBIR fixture corpus and golden characterization gate must exist before scoring or UI restructuring.
5. A packaged VSIX acceptance gate must exercise the generated extension/backend boundary on at least one representative fixture and verify package contents; the complete target matrix remains a release gate where the runner/environment supports it.
6. Version, target, package-content, and artifact-provenance checks must fail authoritatively in CI/release workflows.
7. The supported v1.0 scope and unsupported/deferred boundaries must be documented in current-state authority, including advisory-only Fabric App Review and deterministic-only mutation execution.

### Improvements that may follow characterized behavior

- staged decomposition of `PbirScoringService`, `App.tsx`, `PbirScorePanel.ts`, and broad contract/payload modules;
- namespace/module or assembly separation for scoring, authoring, transport, and experimental code;
- schema-first contract generation;
- ratcheted coverage and deeper CodeQL/SBOM/provenance controls;
- a real privacy-reviewed telemetry implementation or removal of the no-op seam;
- consultant deliverables/export enhancement after stabilization.

## Architecture design

### Protected boundaries

- Backend `ScoreResult` and page-score outputs remain authoritative.
- Normalized findings remain the shared issue model.
- Surface, analyzer, and analyzer profile remain separate concepts.
- Fabric App Review remains an advisory analyzer over a Fabric App surface; it does not gain execution authority.
- AI proposal enrichment remains advisory-only.
- Preview/apply/rollback remains the only deterministic mutation path.
- Repository snapshots remain analyzer-independent and are reused across evidence domains.
- Host/webview messages remain a versioned, validated protocol boundary.
- Selected page state is clamped against the current score payload page count.

### Near-term C# boundary

The first architectural move is a dependency inventory and architecture test suite, not an assembly diagram. The composition root is `service-dotnet/RpcHost/Program.cs` and `AnalyzerRpcDispatcher.cs`; its reachable graph must be recorded for scoring, tree discovery, materialization, authoring, and dormant discovery/provider services.

Default recommendation:

1. Keep the current assembly shape during release recovery and characterization.
2. Introduce durable namespaces/modules and explicit interfaces around scoring, mutation/authoring, transport/contracts, and experimental services.
3. Enforce forbidden dependencies with architecture tests.
4. Split assemblies only where the graph demonstrates that compile/package isolation reduces shipped surface or prevents accidental reachability.

If assembly splitting is approved later, use durable domains (`Domain`, `Scoring`, `Authoring`, `Transport`, and a non-shipped `Experimental` boundary), not phase-number assemblies. No split is allowed to change score or mutation behavior during characterization.

### Near-term score workspace boundary

`App.tsx` and host orchestration should be reduced by responsibility, not line count. Proposed feature ownership is Overview, Issues, Fix Plan, Review Summary, Story Assessment, Rendered Review, Evidence, and Readiness, with shared hooks/reducers for filters, expansion, navigation, and selected page. Rendering modules consume already-computed presentation models; they do not decide scoring-domain rules.

The first UI refactor must be a behavior-preserving extraction behind tests. Any golden or DOM behavior change is an explicit review decision, never an incidental result of moving code.

## Characterization and fixture design

Create a sanitized, versioned corpus under a repository-approved fixture location, with a manifest that records fixture purpose, schema/profile, expected support state, and privacy provenance. The first corpus should cover:

- one minimal valid report;
- multi-page and hidden-page navigation;
- bookmarks/interactions;
- custom visual, Deneb, and HTML Content evidence;
- malformed/partially unsupported input;
- a larger traversal/performance input;
- a mutation-safe copy for preview/apply/rollback;
- one Fabric App repository fixture for advisory review.

Golden output should include total and category scores, findings and codes, severity, evidence, readiness, diagnostics, deterministic fingerprint, and supported mutation preview results. Golden approval is controlled: a changed result requires a reviewed manifest entry describing the intentional behavior change, affected fixtures, before/after summary, and approval reference. No test may update goldens automatically.

## Contract design

Evaluate JSON Schema first because the current boundary is JSON-RPC/JSON payload based and already has runtime validation. Compare it against an IDL only if generated C# and TypeScript ergonomics or versioning needs justify the added toolchain.

The contract should have:

- a stable envelope with protocol version and analyzer/surface/profile identity;
- analyzer-specific payloads rather than one unlimited universal object;
- generated C# DTOs and TypeScript types;
- checked-in compatibility fixtures;
- additive/minor and breaking/major compatibility rules;
- unknown-field tolerance tests;
- initialization version negotiation;
- CI freshness checks proving generated files match the schema.

The existing `scorePanelProtocol.ts`, `scoreResultPayload.ts`, C# score models, and authoring/materialization RPC models are migration inputs, not parallel permanent authorities.

## Packaged acceptance design

The acceptance harness must build from a clean workspace, create or consume the target VSIX, inspect package contents, install/load it in a supported VS Code test environment where available, start the packaged backend, perform initialization/handshake, score a representative fixture, compare deterministic output, preview one supported mutation, safely apply/rollback on a disposable copy, and export one supported review output. It must record logs, package manifest, target, version, source commit, fixture fingerprint, result fingerprint, and checksums.

Where a full VS Code GUI is not practical in CI, split the proof into a deterministic packaged host/RPC harness plus a VS Code extension smoke test. Do not call source-level Jest tests a substitute for package acceptance.

## Prevention controls

| Defect class | Fix | Preventive control | Enforcement location |
|---|---|---|---|
| Broken main/failing CI | diagnose shared failure and restore green matrix | required status checks and no direct main pushes | GitHub ruleset + PR CI; focused pre-push subset |
| Release target drift | central target manifest drives workflows/docs/package names | target matrix validator and package-content validator | source manifest + PR CI + release CI |
| Version drift | choose one extension release version and explicit backend compatibility version | version consistency validator and tag gate | package metadata, backend metadata, docs validator, release CI |
| C#/TypeScript drift | schema-first generated DTOs/types and compatibility fixtures | generation freshness and compatibility tests | contract source, generated directories, PR CI |
| Scoring regressions | corpus and reviewed golden outputs | deterministic characterization gate with explicit approval process | fixture manifest/goldens + PR/release CI |
| Packaged failures | clean VSIX acceptance and backend lineage | packaged smoke test, package allowlist, checksum/provenance manifest | release CI |
| Architecture erosion | explicit dependency graph and boundaries | architecture tests and composition-root allowlist | backend/extension tests + PR CI |
| Monolith regrowth | feature/domain modules with thin orchestration | boundary tests, ownership checklist, advisory complexity signal | source layout, PR template, CI advisory report |
| Generated artifact drift | decide retain/remove and prove lineage | clean build, stale-output purge, SHA-256/SBOM/provenance | packaging scripts + release CI |
| Documentation drift | current authority and generated fact checks | links/version/target/command validation | docs checker + PR CI |
| Experimental leakage | map reachability and isolate registration | production composition allowlist and forbidden dependency tests | backend architecture tests + package inspection |
| Telemetry ambiguity | remove or explicitly disable the seam | test that no event leaves process until an approved provider exists | telemetry tests + privacy review gate |

## Safety and rollback

- Release recovery changes are gate-first and should be independently revertible.
- Fixture additions must be sanitized and tracked by manifest; never commit customer PBIR content.
- Characterization precedes refactoring; a failed golden is evidence, not a reason to rewrite the expected output.
- Mutation acceptance uses disposable copies and must verify rollback leaves the original unchanged.
- Generated binaries are never manually edited. If retained temporarily, a manifest and clean rebuild must prove their source lineage.
- Assembly or schema migration requires compatibility fixtures and a rollback point before deleting old authorities.

## Explicit decision points

Approval is required before implementation for:

1. final supported platform/target matrix, especially `win32-arm64`;
2. manual versus automated Marketplace publication authority;
3. disposition and interim policy for checked-in backend binaries;
4. JSON Schema versus another IDL and generated-code toolchain;
5. backend assembly split versus namespace/module-first boundary;
6. exact v1.0 scope classification for Design Studio, local generation, governance, Fabric App review, rendered review, AI enrichment, and telemetry;
7. minimum packaged VS Code acceptance environment and which target matrix runs where.

## Out of scope

No new Visual Intelligence, broad report-generation, enterprise-governance, provider execution, deployment, or other roadmap capability is included. Dormant/provider code is mapped and guarded, not deleted solely because it is dormant. Scoring behavior is not intentionally changed during characterization.
